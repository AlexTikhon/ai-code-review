# Architecture decisions

## Orchestration

LangGraph was removed. The review is an explicit linear pipeline with no checkpoint/resume or conditional graph behavior, which keeps dependency injection, fatal short-circuiting, and the single request budget easy to follow. This also removed the advisory-bearing LangChain/LangSmith transitive tree without a major-version migration. No workflow framework, agent loop, or DI container is used, and the former `createReviewerGraph()` compatibility facade (and `src/graph/`) no longer exists.

```text
CLI (args, output, exit codes)
 |  requestFromCliArgs()                          src/cli/request.ts
 v
bootstrap: loadConfig + createProviders           src/cli/run-review.ts, src/cli/providers.ts
 |
 v
runReviewPipeline(args, deps)   compat wrapper    src/review/pipeline.ts
 |
 v
executeReviewPipeline(request, config, runtime)   src/review/pipeline/run-review-pipeline.ts
 |
 +--> ingest   -> Git / GitHub adapters (or an injected source)
 +--> filter   -> trusted ignore policy + privacy filter + work limits
 +--> context  -> persisted index -> prepared (runtime) index
 +--> analyze  -> ReviewModel port, EmbeddingAdapter port, review cache
 |                bounded worker pool, one FileReviewOutcome per file
 +--> finalize -> deterministic aggregation, status, summary
 |
 v
ReviewResult --> text | JSON | SARIF
```

`executeReviewPipeline` only sequences stages. Each stage is a plain function in `src/review/pipeline/` that takes explicit inputs and returns a value:

| Stage    | Modules                                                | Responsibility                                                                                                                |
| -------- | ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| ingest   | `ingest-stage.ts`                                      | Collect a `ReviewSource` from Git/GitHub. A failure is fatal and short-circuits the run.                                      |
| filter   | `filter-stage.ts`, `../request-plan.ts`                | Choose the trusted ignore policy, apply privacy/ignore/type/work-limit rules, plan full-request segments, compute truncation. |
| context  | `context-stage.ts`                                     | Build or refresh the persisted index, then compile it once into a `PreparedRepositoryIndex`. Failure degrades to diff-only.   |
| analyze  | `analyze-stage.ts`, `review-file.ts`, `concurrency.ts` | Review eligible files through the worker pool; every file returns a `FileReviewOutcome`.                                      |
| finalize | `aggregate.ts`, `finalize-stage.ts`                    | Fold outcomes in deterministic order, decide status and summary, build index-only and dry-run results.                        |

**Source admission.** Which paths may be read, reviewed or indexed is decided in three places that share the same rules and never relax each other. (1) Local collection (`ingest-stage.ts` -> `getLocalDiff`) asks `pathAllowed` for the destination _and_ the `previousFilename` of every tracked rename or copy before it runs the per-file `git diff`, so a protected origin's bytes are never read into the source. (2) `filterReviewFiles` independently checks the destination and the origin against the mandatory sensitive-path rules (`evaluateFilePrivacy`, immune to `!` negation) and the trusted ignore policy (base revision in PR mode, never the proposed head); this is also the only check for GitHub and injected sources. A refused file stays in `source.files` with its metadata, is reported as skipped (`sensitive_path`/`ignored_by_user`) and is not counted as reviewed. (3) The context index scan (`scanSourceFiles`) applies the mandatory rules, the trusted ignore, a generated/vendor rule and an `excludePaths` set before any source is read, chunked or embedded, in both working-tree and immutable-revision modes. `excludePaths` carries every destination step 2 refused (`filterStage` -> `contextStage`), which is how a protected rename cannot re-enter through the index: `renamed.ts` looks ordinary by name. The generated/vendor rule (`isGeneratedOrVendorPath`) matches whole path components - `node_modules`, `bower_components`, `vendor`, `dist`, `build`, `.next`, `coverage` - and `*.min.js`, so `src/node_modules-helper.ts` and `src/dist.ts` stay indexable; like the mandatory rules it cannot be re-included by an ignore negation. Because tracked files are indexed, `.gitignore` alone never excluded them.

`ReviewRunRequest` (`target`, `contextMode`, `dryRun`, `indexOnly`) is the application-level command. Output format, help text, and the severity threshold are CLI concerns and never enter the core. `runReviewPipeline(args, deps)` is kept as a thin compatibility wrapper that translates `CliArgs` and delegates; it does not compose providers.

Console rendering is a CLI event consumer. Stages emit structured events (run ID, stage, filename, `durationMs`, attempt, counts, revision/snapshot, usage, cache-hit counters) for `ingest`, `filter`, `index`, `retrieve`, `analyze`, and `finalize`. Events never carry source code, diffs, prompts, PR text, or secrets, and there is no external telemetry. The `finalize` event's `durationMs` is the whole run; `data.finalizeMs` is the finalize step alone.

## Model boundary

```text
                 Review pipeline
                       |
         +-------------+-------------+
         |                           |
    ReviewModel                 Retrieval
     /       \                       |
    /         \                EmbeddingAdapter
OpenAI       Anthropic               |
adapter      adapter          OpenAI embeddings
```

The two provider concepts are orthogonal: any review adapter can run with or without an embedding adapter, and adding the Anthropic review adapter did not add or change an embedding adapter. `AI_REVIEW_PROVIDER` (default `openai`) is validated in `loadConfig` and acted on in exactly one place, a `switch` in `createProviders()`; no pipeline stage branches on a provider name.

`ReviewModel` and `EmbeddingAdapter` are the provider ports. The pipeline holds only these interfaces and never constructs a provider: `createProviders()` in `src/cli/providers.ts` is the single place that picks concrete adapters. It builds the OpenAI model only when the effective configuration authorizes external transmission, and the embedding adapter only for hybrid retrieval with separate embedding consent. A run without a model fails closed before any stage runs, except `--dry-run` and `--index`, which never need one. Production adapters use structured JSON, and each translates its provider's response into the one domain `ModelResult`, validated by the shared zod schema (`src/schemas/review.schema.ts`). The OpenAI adapter uses a `json_schema` response format. The Anthropic adapter uses `output_config.format` structured outputs with the same JSON Schema rewritten into Anthropic's subset (array bounds and type unions removed; the zod validator still enforces the bounds). A truncated, refused, malformed or schema-invalid answer is a typed `ReviewModelError`, never a result (see Failure semantics). Neither adapter owns prompt text: the shared prompt layer assembles one trusted system message and one untrusted user message, and an adapter only maps those onto its API. The Anthropic adapter disables the SDK's built-in retries so `executeModel` stays the only retry loop and `ExternalRequestBudget` sees every HTTP attempt. It passes the abort signal to the request and translates every SDK failure into a `ReviewModelError`; Anthropic SDK error classes are inspected only inside that adapter. Provider usage is normalized to `{inputTokens, outputTokens, actual}`: Anthropic's cached-token counts are folded into `inputTokens`, and a missing or partial usage block yields `actual: false` (zeros plus the pipeline's estimate flag), never a guessed count. offline tests and evaluation inject deterministic adapters through `ReviewRuntime`. Adding a provider means implementing a port and composing it in `providers.ts`; the pipeline does not change. Trusted review rules are a system message. Metadata, code, comments, diffs, and retrieved chunks are clearly labeled untrusted user data. Prompt/schema/policy versions participate in cache keys.

## Failure semantics

```text
SDK / HTTP failure
        |
  provider adapter            (the only code that knows SDK error classes)
        |
  ReviewModelError {kind, provider, retryable, statusCode?, retryAfterMs?, code?}
        |
  executeModel                (one retry loop; budget reserved per attempt)
        |
  SegmentFailure {status, ReviewError{code, provider, retryable}}
        |
  FileReviewOutcome -> aggregate -> ReviewResult.errors
```

`src/model/errors.ts` defines one small error class and a closed set of kinds: `authentication`, `rate_limit`, `timeout`, `network`, `provider_unavailable`, `invalid_request`, `unsupported_model`, `malformed_response`, `response_truncated`, `refused`, `aborted`, `unknown`. HTTP status mapping is shared by both adapters (401/403 authentication, 404 unsupported_model, 408 timeout, 429 rate_limit, 409 and 5xx provider_unavailable, other 4xx invalid_request). Messages are fixed text built by the adapter (`<Provider> error <status>`, `connection error`, `request failed`); the provider's own error message is never read into the result, because it can echo the request, i.e. source code. The one provider-supplied field kept is `code`, and only when it is exactly one of a small allowlist of known identifiers (`safeProviderCode`, e.g. `model_not_found`, `rate_limit_error`); any other code or type string is dropped, not truncated, and the `ReviewModelError`/`EmbeddingError` constructors enforce this for every producer. Status, kind, retryability and `Retry-After` timing are unaffected. Response bodies, request text, thrown messages and raw SDK objects are never retained, and an adapter that leaks a raw error is treated as `unknown` and not retried. The messages of typed errors an adapter constructs itself are its own responsibility and must be fixed text. Not covered: GitHub and Git source errors (see below) keep their own bounded diagnostics.

**Retry.** `executeModel` consumes only normalized metadata. An attempt is retried iff the error is `retryable`, attempts remain, and neither the total deadline nor that attempt's own timeout has fired (a timed-out request may still be processed by the provider, so it is never duplicated). `retry-after` is honored up to ten seconds. Every attempt passes through the request budget first, so a retry costs a request, a cache hit and an abort before send cost none, and an unauthorized run never reaches a provider. Malformed structured output is retried within the attempt limit; truncation, refusal, authentication, invalid request and unsupported model are not. `executeModel` returns failure as data (`{ok:false, error, attempts}`) so callers learn the attempts actually made.

**Outcomes.** Each reviewed segment ends in one of: `success` (findings or a clean result, possibly an abstention); `invalid_evidence` (the model answered validly but cited evidence that was not supplied; the response is discarded, never cached or retried, and its tokens are still counted); `model_failure` (a provider failure or an unusable response: any `ReviewModelError` except `aborted`); `aborted` (deadline or caller cancellation); `internal_failure` (request budget, prompt assembly or retrieval). Only `success` can contribute to a reviewed file, so no failure path can read as clean. A failure also produces a `ReviewError` with a stable `code` (`MODEL_RATE_LIMIT`, `MODEL_RESPONSE_TRUNCATED`, `MODEL_MALFORMED_RESPONSE`, `MODEL_INVALID_EVIDENCE`, `REQUEST_BUDGET_EXHAUSTED`, `REVIEW_ABORTED`, `ANALYSIS_FAILED`, ...), the `provider` and `retryable`; consumers should branch on `code`, not `message`. The default `AI_REVIEW_MAX_OUTPUT_TOKENS` of 1200 is unchanged: nothing in the code shows it truncating the current schema in normal use, so a truncated answer is surfaced as `MODEL_RESPONSE_TRUNCATED` naming the setting rather than the default being guessed at.

**Prompt size.** The input-size estimate (`src/prompts/estimate.ts`) is the UTF-8 byte length of the shared system and user text plus the shared response schema and a fixed framing allowance. It never serializes any provider's request, so it is the same for every provider; real token counts come only from the provider's response.

**Request planning.** `src/review/request-plan.ts` is the one pure place that decides how big a request is and where segments end. It reads nothing, calls nothing and knows no provider. With `usable = maxInputTokens - maxOutputTokens`, a segment's _mandatory request_ is the system text, redacted/bounded metadata and path, the segment text, its serialized line map, the valid-range trailer, the response schema and the framing allowance. The filter stage calls `planReviewSegments`, which delegates line-boundary packing to `planPatchSegments` (`patch.ts`) with a fit predicate built from the same renderers `assembleReviewPrompt` uses (`renderReviewMetadata`, `renderMandatoryRequest`, `renderReviewUser`), so a candidate segment is measured exactly as it will be sent. A segment must satisfy both the independent `maxPatchTokens` cap and `mandatory <= usable`. Every candidate is rebuilt from its own lines, so offsets, line mappings, valid ranges and the content-derived id are always segment-local; fit is monotonic in line count, so lines are packed by galloping then bisecting. A line that does not fit alone becomes non-citable `complete: false` fragments (original coordinates kept, never a positive range); a line that cannot be fragmented is dropped. Content past `maxSegmentsPerFile`, a fragmented line, or a dropped line makes the plan `truncated` (file `truncated`, review `partial`, never complete). A file whose fixed request leaves no room for any content is omitted (`work_limit`), so one unplannable file does not fail its siblings. Review execution consumes `file.segments` as planned. `assembleReviewPrompt` packs retrieved context, in retrieval order, only into `min(maxContextTokens, usable - mandatory)` and still re-checks the final estimate; failing that check means the planner invariant was violated (`ANALYSIS_FAILED`), not that a diff was dense. `requestBudgetProblem` rejects impossible cross-field budgets (output reservation not below the input allowance; fixed prompt leaving no room for a diff) in `loadConfig` and again at the start of the pipeline, before any source, index or provider work.

**Dry-run.** `finalizeDryRun` derives per-segment figures with the same estimator over the planned segments, so in diff mode `estimatedRequests` and `estimatedInputTokens` equal what execution builds. They are planned logical requests, not paid calls: retries, cache hits and provider failures are unknown. In context modes the dry run still makes no embedding or model call and cannot know retrieval results, so it reports the mandatory estimate plus `contextTokenBound` (the per-request context allowance, summed) and `inputTokenBound`, a ceiling rather than a prediction. All figures are conservative application-level estimates, not provider billing-token counts.

Findings require severity, category, confidence, evidence, and stable IDs. The diff is parsed once into persistent old/new line mappings before segmentation. Direct evidence must cover only complete added lines actually present in that segment; line zero, omitted lines, gaps, and fragments of oversized lines are rejected. Deletions retain old-line mappings for inspection but cannot be emitted as positive-file locations: a deletion-related finding must anchor to a supplied added line or a complete retrieved context range. Invalid locations are rejected before a response can enter the cache. Deduplication uses normalized finding identity. A valid citation means “this supplied location was referenced,” not “the claim is proven.” The response schema supports abstention.

## Source ingestion boundary

```text
Review pipeline: ingest stage
        |
   +----+-----------------------------+
   |                                  |
Local Git (local.ts)             GitHub (pulls.ts: PR snapshot)
   |  execFile git, no shell          |  validates every response (schemas.ts, zod)
   |  classifyGitFailure              |
   |                              GithubRequester (client.ts)
   |                                  |  one HTTP attempt: fetch + classifyGithubResponse (http-errors.ts)
   |                                  |  wrapped by executeSourceRequest (request-executor.ts)
   |                                  |    attempt timeout + caller signal, retry, Retry-After, deadline
   +----------------+-----------------+
                    |
        SourceError {kind, source, retryable, statusCode?, retryAfterMs?, code?}
                    |
        ingestFailure -> ReviewError {code, source, retryable}   (never parses a message)
```

`src/review-sources/errors.ts` has one small error class and a closed set of kinds: `authentication`, `authorization`, `not_found`, `rate_limit`, `timeout`, `network`, `provider_unavailable`, `invalid_response`, `revision_changed`, `coverage_incomplete`, `aborted`, `configuration`, `unknown`. Rate limit, timeout, network, provider-unavailable and revision-changed are retryable. All GitHub status and header interpretation stays in `src/review-sources/github/`: 401 is authentication; 404 is not-found; 408 is a timeout; 5xx is provider-unavailable; 429 is a rate limit; and a 403 is a rate limit only when GitHub says so (`x-ratelimit-remaining: 0`, a valid `Retry-After`, or its documented secondary-limit wording), otherwise a permission failure that is never retried. Error messages carry the operation and status, plus GitHub's own short `message` (bounded and scrubbed) for 4xx; never a response body, URL, credential or repository text. Git failures use the same class with `source: "git"` and a short code (`not_a_repository`, `invalid_ref`, `no_merge_base`, `git_unavailable`, `git_command_failed`); stderr is never kept, and a base ref beginning with `-` is rejected before it can reach Git's argument parser.

**Retry.** `executeSourceRequest` is the only retry loop (every GitHub operation is a GET, so retrying is safe). At most 3 attempts. Between attempts it waits the provider's `Retry-After` (seconds or HTTP date), or, for an exhausted primary rate limit, until `x-ratelimit-reset`; otherwise 250 ms then 500 ms. A secondary rate limit without any header waits the minute GitHub asks for, which exceeds the cap. A wait longer than 10 s, or one that does not fit before the total deadline, is not taken: the request fails with a retryable `rate_limit` carrying `retryAfterMs`, so a CLI run never sleeps for minutes. The wait, the per-attempt timer, the clock and `fetch` are injectable, so no test waits.

**Timeout and cancellation.** Each attempt's signal is `AbortSignal.any([caller signal, attempt timer])`; a caller signal never replaces the per-attempt timeout (`AI_REVIEW_REQUEST_TIMEOUT_MS`). Overall cancellation outranks everything: once the caller signal (the total deadline) has fired the request is `aborted`, is never retried, the wait is interrupted and no further attempt or page request starts (the signal is also checked before every page, and before the first request, so an already-aborted run makes zero HTTP calls). When only an attempt's own timer fired, the failure is a retryable `timeout`.

**Snapshot invariants.** PR collection reads metadata, every file page, then the trusted base-revision ignore policy (sequentially, so a failure never leaves a sibling request running), then reads the metadata again. Retries happen inside individual requests and never weaken the final check: if base SHA, head SHA or `changed_files` differ, the result is a retryable `revision_changed`; a file repeated across or within pages (a push shifting pagination) is also `revision_changed`, never merged. If the revision is stable but fewer files arrived than `changed_files`, or the PR reports more than GitHub's 3000-file limit (checked before paginating), collection fails with `coverage_incomplete`; coverage is never reported complete from a partial list. Only a real 404 for `.ai-reviewer-ignore` at the base SHA means the optional file is absent; a non-base64 encoding, a directory, or a malformed payload there is `invalid_response`, and 401/403/429/5xx remain failures. A revision SHA must look like a Git revision (no leading `-`).

**Results.** An ingestion failure is a fatal `ReviewError` with `code` (`GITHUB_AUTHENTICATION_FAILED`, `GITHUB_AUTHORIZATION_FAILED`, `GITHUB_NOT_FOUND`, `GITHUB_RATE_LIMIT`, `GITHUB_PROVIDER_UNAVAILABLE`, `GITHUB_INVALID_RESPONSE`, `GITHUB_REVISION_CHANGED`, `GITHUB_COVERAGE_INCOMPLETE`, `GIT_NOT_A_REPOSITORY`, `GIT_INVALID_REF`, `GIT_COMMAND_FAILED`, `SOURCE_TIMEOUT`, `SOURCE_NETWORK`, `SOURCE_CONFIGURATION`, `SOURCE_FAILED`; cancellation is the shared `REVIEW_ABORTED`), `source` and `retryable`. The result schema is 1.4.0 (additive; 1.4.0 extends the dry-run manifest, see Request planning). GitHub source requests are operational reads, not AI inference: they are bounded by the retry policy and total deadline and never consume `AI_REVIEW_MAX_REQUESTS`. Diagnostics are `source` stage events (`github.request_started`, `.request_retry`, `.request_succeeded`, `.request_failed`) with operation (`pull`, `files`, `trusted_policy`), page, attempt, status, error kind, retryability, `waitMs` and duration; never URLs, tokens, bodies or patches. There is no request cache and no GitHub write operation.

**Review-source identity versus context identity.** `ReviewSource.repositoryId` says where the change comes from (the checkout hash in local mode, `owner/repo` for a PR, possibly a fork) and is used for reporting. The repository-context index describes the local bytes it was built from, so it is keyed by `ReviewSource.contextIdentity.localRepositoryId`, the hash of the canonical checkout root (`git rev-parse --show-toplevel`, real path). No remote URL is consulted: a repository may have none, remotes are renamed and may embed credentials, and a PR may come from a fork whose commits sit in the same object database. The same checkout therefore uses one index whether it is reviewed as `--local` or as any PR, while the cache namespace (derived from the checkout path) keeps different checkouts apart, so a different checkout can never load another's index even when both report the same `owner/repo`. If an index file is copied between namespaces its identity no longer matches and it is rebuilt. A linked Git worktree shares an object database with its main work tree but has its own files, and a local index reads files, so identity is per work tree (not `--git-common-dir`); reuse across worktrees would risk mixing working-tree content. An index written before this split (PR mode stored the lowercase `owner/repo`) is adopted at load: only the identity label and the identity-derived chunk ids change, file entries and vectors carry over, no embedding provider is called, and the next publication writes the new identity (event `identity_migrated`). Only that legacy shape is adopted; any other differing identity is `incompatible`. Local indexes already used the same hash and need no migration.

## Embedding failures and retries

Embeddings are a separate provider domain from the review model, with their own typed error and their own retry executor. They never depend on `AI_REVIEW_PROVIDER`.

```text
index batch / query embedding
        |
  executeEmbeddingRequest       (src/retrieval/embedding-execution.ts: the only retry owner)
        |   assertReady          misconfiguration fails before any budget is spent
        |   reserve budget       one unit per attempt, taken only when that attempt starts
        |   per-attempt timeout  AbortSignal.any([total deadline, attempt timeout])
        v
  EmbeddingAdapter.embed         exactly one provider attempt, no retry inside
        |
  EmbeddingError {kind, provider, retryable, statusCode?, retryAfterMs?, code?}
        |
  retry decision -> wait (Retry-After | jittered backoff) -> next attempt
        |
  validate answer -> vectors -> checkpoint (index-update) -> atomic publish
```

`EmbeddingError` (`src/retrieval/embedding-errors.ts`) has a closed set of kinds: `authentication`, `rate_limit`, `timeout`, `network`, `provider_unavailable`, `invalid_request`, `unsupported_model`, `malformed_response`, `dimension_mismatch`, `aborted`, `unknown`. Rate limit, timeout, network and provider-unavailable (5xx, 409) are retryable; everything else is permanent. The HTTP status table and `Retry-After` parsing are the model domain's (`kindForHttpStatus`, `retryAfterFromHeaders`), reused rather than copied; the error class and the executor are separate so a rate limit on embeddings (`EMBEDDING_RATE_LIMIT`) is never confused with one on the review model (`MODEL_RATE_LIMIT`). `OpenAIEmbeddingAdapter` is the only code that translates transport failures; neither the executor nor the index code inspects status numbers, SDK classes or message text. Messages keep the status and an allowlisted provider error code only (the same `safeProviderCode` vocabulary as the review models), never the response body (it can echo source text), thrown error text, or a credential. The adapter calls the global `fetch` directly, which does not retry, so one attempt is one HTTP request; there is no SDK retry layer to disable, and a test proves three application attempts produce exactly three requests.

**Policy.** At most `AI_REVIEW_EMBEDDING_MAX_ATTEMPTS` (default 3) attempts per request. Between attempts: a valid provider `Retry-After` (`retry-after-ms` or seconds) is honored exactly, clamped to 10 s; otherwise capped exponential backoff from `AI_REVIEW_EMBEDDING_RETRY_BASE_MS` (default 250 ms: 250, 500, 1000 ...) with equal jitter, uniform in [step/2, step]. The wait, the jitter source and the sleep are injectable, so no test waits. Each attempt has its own timeout (`AI_REVIEW_REQUEST_TIMEOUT_MS`), and an attempt timeout is retryable; the total deadline (`AI_REVIEW_TOTAL_TIMEOUT_MS`) and caller cancellation never are. A retry whose wait is not shorter than the time left before the total deadline is not started: the request fails with a non-retryable `timeout` rather than sleeping into an inevitable abort.

**Budget.** One adapter call is one `ExternalRequestBudget` unit. A retry is therefore never free, and a retry's unit is reserved only when its attempt is about to start, never before its wait. Checkpoint hits, reused vectors, cancellation before send, a missing credential and an exhausted budget consume nothing further. Budget exhaustion surfaces as `RequestBudgetError` / `REQUEST_BUDGET_EXHAUSTED`, an application limit, not as an `EMBEDDING_*` provider failure.

**Cancellation.** The caller's signal is checked before each attempt, after the reservation, and during the wait; an abort ends the request without a further attempt and is reported as `REVIEW_ABORTED`.

**Response validation.** A 2xx is not yet a success. The adapter rejects a non-JSON body, a missing `data` array, a wrong count, a missing, duplicate, non-integer or out-of-range `index`, and a non-numeric embedding; it places each vector by its explicit `index`, not by position. The executor then checks the count, the dimension (the model's known dimension, else the batch's own) and finiteness for every adapter. All of these are non-retryable (`malformed_response`, `dimension_mismatch`): a deterministic bad payload would be paid for again and come back the same.

**Batches and checkpoints.** Each index batch is its own request, so a transient failure retries that batch alone and never re-runs a completed one. After a batch succeeds its vectors join the checkpoint set, which is persisted every eighth batch and always once more when the run fails, is cancelled or exhausts its budget (unchanged policy). If one batch ultimately fails, the run still stops: later batches do not start, the canonical index is untouched, and the vectors of every earlier batch are in the checkpoint for the next run. Index-build failures are reported in `ReviewResult.errors` (stage `index`, non-fatal, review continues without repository context) with the codes `EMBEDDING_*`, `REQUEST_BUDGET_EXHAUSTED` or `REVIEW_ABORTED`; a failed query embedding for a segment is a `retrieve`-stage error on that file.

**Diagnostics.** Events with stage `embedding` and the messages `embedding.request_started`, `.request_retry`, `.request_succeeded`, `.request_failed` carry provider, model, attempt, batch size, duration, error kind, retryability, `retryAfterMs`, `waitMs` and the remaining budget; never texts, vectors, credentials or provider bodies. The `index` completion event adds `embeddingRetries`.

**Shared infrastructure.** `executeModel` and `executeEmbeddingRequest` are deliberately two small executors that share primitives (the status table, `Retry-After` parsing, the provider-code allowlist, `ExternalRequestBudget`), not one generic loop. Their rules differ where it matters: the model executor never retries an attempt timeout (a half-finished generation may still be billed) and returns failure as data, while the embedding executor retries timeouts (embedding is idempotent and cheap) and throws, because index construction already aborts by throwing. A shared loop would have needed a flag for each of these differences.

**Batch-size adaptation: not implemented.** Batches are 32 chunks of at most 800 tokens (about 26k tokens per request), far below OpenAI's embedding limits (8,191 tokens per input, 300k per request, 2,048 inputs), and no payload-too-large failure is reproducible with the current sizes. Splitting a failed batch would complicate request accounting for no demonstrated need.

## Retrieval and invalidation

TypeScript/JavaScript are parsed with the runtime TypeScript compiler API. Top-level functions/classes/interfaces/types/enums/variables produce symbol chunks; imports, multiline declarations, strings, comments, templates, and nested syntax use AST boundaries. Source outside recognized declarations is retained in explicit file chunks. Other supported source extensions use line-window fallback chunks. Oversized physical lines become mapped `contentComplete=false` fragments rather than silently disappearing.

All chunks obey the conservative UTF-8-byte budget for ASCII and multibyte input. Retrieval generates lexical/symbol and semantic shortlists independently, merges and deduplicates their union, then ranks it. Stored/query vector counts, finite values, provider identity, and dimensions are validated; incompatible vector spaces fail explicitly. Same-file chunks remain eligible with a small boost because helpers and enclosing definitions can be relevant. Candidate count, top-k, threshold, and budgets are configurable experimental defaults. Selected IDs, scores, and reasons appear in the result.

The persistent store is a small set of mode-0600 files under a repository-specific directory in the current user's OS cache (a manifest, a JSON metadata file and a binary vector file; see the next section). Indexes carry repository and snapshot identity. Local snapshots hash `HEAD` plus working-tree patch identities and index the working tree. PR indexes enumerate and read the exact head Git tree, independent of the checkout’s current `HEAD` or dirty/untracked files; the trusted ignore policy remains the API-fetched base-revision policy. Rebuilds are incremental per file (next section), and vector keys cover the exact normalized input (including path/signature/content), provider/model/version, configured/default dimension identity, chunker version, and chunk budget. Retrieval rejects repository/revision mismatch.

Cross-file verification is bounded by the same top-k and prompt token limit: retrieved definitions/import neighbors can be cited as concrete evidence. No recursive agent or unbounded whole-repository prompt is used.

## Repository index: incremental update and prepared runtime form

```text
Persisted index (schema 3), under <user-cache>/<repository-namespace>/
   repository-index.json                 manifest: the only mutable file; names one generation
   repository-index.generations/
      index-<generation>.json            metadata: files, chunks, per-chunk input hashes, vector layout
      vectors-<blobId>.bin               64-byte header + float64 little-endian rows; numbers only
        |
        v   readIndex(): manifest -> metadata (size, sha256, schema) -> blob (size, header, sha256, finite check)
RepositoryIndex (runtime)
   +-- files   : per-file identity (content hash, size, blob id / mtime hint, chunk ids)
   +-- chunks  : in repository order, each owned by exactly one file
   +-- inputHashes[i] : embedding-input hash of chunks[i] (persisted, never re-derived for unchanged chunks)
   +-- vectors : VectorStore, one segment per embedding space
          +-- vectors      Float64Array: a view of the buffer the blob was read into
          +-- cacheKeys / inputHashes   parallel to the rows
          +-- squaredNorms Float64Array, derived at load, never persisted
        |
        v   updateRepositoryIndex(previous, currentFiles, deps) -> next
   incremental reconciliation
        |      unchanged -> reuse chunks (rebound to the new revision), their hashes and vector rows
        |      modified  -> re-read, re-chunk, embed only inputs without a stored vector
        |      added     -> chunk, embed
        |      deleted   -> dropped with its chunks, vectors and lexical entries
        v
   validated in memory, then published as a new generation (blob + metadata first, manifest last)
        |
        v   prepareRepositoryIndex()
PreparedRepositoryIndex (runtime only: Maps, never serialized)
   +-- chunks in deterministic order, with embedding input hashes
   +-- vectorsByInputHash        : O(1) stored-vector lookup (refs into the store, no values)
   +-- lexical (LexicalIndex)    : postings, symbol, path and import lookups
   +-- semantic (per embedding)  : exact-search space, built on first hybrid query
          +-- vectors      Float64Array, row r = chunk ordinal r: the store's own array when the
          |                rows are the whole segment in order, otherwise a gathered copy
          +-- norms        Float64Array, squared norms (the store's, or gathered with the rows)
          +-- ordinals     row -> chunk (read only for the winning rows)
```

**Persisted form (schema 3).** The index is a manifest plus one generation: a metadata JSON and, when any vector exists, a binary vector blob (`src/retrieval/index-generation.ts`, `vector-format.ts`, `index-schema.ts`). The metadata is validated with Zod on load: schema, chunker and policy versions, identity and revision on the index and on every chunk, line ranges, one input hash per chunk, and the vector layout (spans, counts, dimensions, file size, checksum). Every chunk must belong to exactly one `files` entry whose path matches, so a reused file can never resurrect another path’s chunks or leave ownerless ones. A file entry records its SHA-256 content hash, size, a Git blob id (revision indexes) or a working-tree mtime hint, and its chunk ids. Reuse is decided by content identity: a blob id, or a content hash after a read. A matching size and mtime only avoids that read, and only for mtimes older than a two-second window, so a file rewritten in the same timestamp tick is never trusted by timestamp. Like Git’s own index, this cannot see a same-size rewrite that also restores the old mtime; `trustFileStat: false` reads and hashes every file instead. PR indexes use blob ids from the tree listing, so unchanged files cost no `git show`.

The metadata holds no vector values. For each embedding space it holds the identity once (provider, model, version, dimension setting, actual dimensions), the byte offset and row count of that space in the blob, and two parallel arrays: the cache key and the embedding-input hash of row `r`. A vector therefore maps to its chunks through its input hash, exactly as before, and a cache key is stored once per vector rather than the identity fields being repeated per vector. Chunker version and chunk budget are index-level, because a vector made under another chunker or budget is unreachable (both are in its cache key) and is not carried into a schema-3 index.

**Per-chunk embedding input hash.** `chunkInputHashes[i]` is the SHA-256 of the exact embedding input of `chunks[i]` (path, signature and content after line-ending normalization), tagged by `inputHashVersion` (`sha256-path-signature-content-v1`). It is persisted so an unchanged chunk is never re-hashed just to find its vector: incremental update carries the stored hash along with the stored chunk (rebinding changes only the revision and id, never the hashed input), and `prepareRepositoryIndex` takes the stored hashes instead of hashing every chunk again. Only created chunks are hashed. The hash is one-way and carries no source text. If the definition of the embedding input ever changes, `EMBEDDING_INPUT_HASH_VERSION` changes with it and an index recorded under the old definition is treated as incompatible and rebuilt rather than trusted. The hash is derived data and is not re-verified on load: like the vectors, it is protected against accidental corruption by the checksums, not against deliberate tampering.

**Generations and crash safety.** The manifest (`repository-index.json`) is the only mutable file. It names exactly one generation and carries the size and SHA-256 of that generation’s metadata file. Every file a generation names is written under a fresh unique name and is never modified afterwards. Publication:

1. write the vector blob under a temporary name (header, rows, SHA-256 computed while writing, `fsync`), or keep the previous blob if the vectors are unchanged;
2. validate the next metadata against the schema readers apply, write it under a temporary name (`fsync`);
3. rename the blob and the metadata to their final names;
4. replace the manifest with one atomic rename. This is the commit point;
5. only then remove the files the new manifest no longer reaches (best effort, counted, never fatal).

The invariant is: _the manifest always names a complete, validated generation, and nothing it names is ever written to after it is named._ A crash or error before step 4 leaves the previous manifest and the previous generation untouched; whatever was written is unreferenced garbage no reader looks at, and a failed publication removes its own files. A crash after step 4 leaves the new generation canonical. There is no instant at which the manifest can name a metadata file without its blob, or a blob that is not fully written, so a process can never observe metadata of one generation with vectors of another. A blob is immutable, so consecutive generations may share one: when an incremental run leaves the vector set unchanged (typically every run that edits no embedded text), the previous blob is kept and only the small metadata is rewritten.

Tests cross the failure points systematically: a simulated crash before and after every filesystem call of a publication (`test/index-faults.ts` wraps the real filesystem and kills it at call `k`) must leave exactly the previous or exactly the new generation; an I/O error at every call before the commit leaves the previous index and no files behind; failures after the commit never turn a published index into an error.

**Retiring generations.** After the commit, the files of the generation just replaced are removed. Unreferenced leftovers (a crashed publisher’s files, including temporary files) are removed only once they are older than an hour, so a concurrent publisher’s in-flight files are never touched; files that do not match the generation naming pattern are never touched at all. A reader that finds a file its manifest names missing rereads the manifest and follows a newer generation if one was published meanwhile; if the manifest has not moved, that is real damage and is reported as `corrupt`. Publication, vector-blob reuse and cleanup are serialized by an exclusive filesystem lock per manifest. No provider work holds that lock. A publisher whose previously loaded blob was retired writes a fresh blob after acquiring the lock. Waiting is bounded to ten seconds and respects cancellation. A lock with a provably dead PID is reclaimed under a separate reaper gate; incomplete or ambiguous owner records fail closed and require manual inspection.

**Binary vector blob.** `vectors-<blobId>.bin`, all numbers little-endian regardless of host:

```text
offset  size  field
     0     8  magic "ACRVECS\0"
     8     4  u32 format version (1)
    12     4  u32 numeric encoding (1 = IEEE-754 binary64)
    16     8  u64 total vector count
    24     8  u64 payload byte length
    32    16  blob id (raw bytes of the 32 hex digits in the file name)
    48    16  reserved, zero
    64     .  payload: for each embedding space in metadata order, count x dimensions float64 values, row after row
```

The metadata gives each space’s offset (relative to the payload), count and dimensions; spans must tile the payload exactly (no gap, overlap, negative or out-of-range offset), and the file size must equal `64 + 8 x Σ count x dimensions`. The blob holds numbers only: no source text, keys, prompts or credentials. Vectors are still sensitive artifacts (an embedding encodes information about its input), so they live exactly where they did before, in the user-owned cache directory outside the repository, with owner-only permissions where the platform supports them; nothing about who may read them changed. Vector values are never logged: store events carry counts, byte sizes, a generation id and the zero-copy flag.

The encoding is IEEE-754 binary64, the representation JSON numbers were already parsed into, so a stored number is bit-for-bit the number that is loaded (including `-0` and denormals), and ranking is identical to the JSON layout. Float32 or quantization would change ranking (see the precision note below) and is not used. Byte order is explicit rather than the host’s: reading and writing swap bytes on a big-endian host (`float64View`, `float64LittleEndianBytes`), tested by simulation. Compression is deliberately not used: it would require inflating the whole blob before use and would defeat viewing the file’s bytes as the search array.

**Integrity.** On load the metadata is checked against the manifest (size, SHA-256, generation id), then the schema; the blob is checked for size (truncation or extra bytes), header (magic, version, encoding, reserved bytes, blob id against the metadata, count and payload length), SHA-256 against the metadata, span layout, and finiteness. The checksum guards against truncation, bit rot and torn writes; it is an integrity check, not authentication, and no signing is involved. It is computed once while writing and once while loading, never per query. Finiteness is checked in the same single pass that derives the squared norms, since a finite sum of squares proves every value finite; a vector whose norm would overflow is rejected when it is built, so such a vector can never be written into an index that could then not be loaded. Any violation is `corrupt`: the index is rebuilt from source and reported, never mistaken for an empty index.

**Load outcomes.** `readIndex()` returns `missing` (no manifest or index file), `valid`, `corrupt` (unreadable, not JSON, any schema or consistency violation, or a manifest whose generation is incomplete, truncated, altered or mismatched), `incompatible` (well-formed but made by another schema version, chunker version, chunk budget, privacy-policy version, input-hash definition or repository) or `stale` (compatible but for a different revision than a caller required). Compatibility is decided from the metadata alone, before the blob is read. Corrupt and incompatible indexes are not reused at all: they are rebuilt from source and reported as a value-free diagnostic in `context.message`. A moved revision is the normal case, not an error. The index refresh reconciles file by file and rebinds each reused chunk to the new revision, which changes only its revision and revision-derived id.

**What is reused when.**

| Change                                                              | Chunks                                            | Vectors                                              | Files read                                                    |
| ------------------------------------------------------------------- | ------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------- |
| Nothing                                                             | all reused                                        | all reused, zero embedding requests                  | none (blob id, or size+mtime hint older than the racy window) |
| New revision, same files                                            | all reused, rebound                               | all reused                                           | none                                                          |
| One file edited                                                     | the others reused; that file re-chunked           | only inputs without a stored vector are embedded     | that file                                                     |
| File added or deleted                                               | others reused; deleted chunks and vectors dropped | new inputs embedded; orphaned vectors pruned         | the added file                                                |
| File renamed                                                        | delete plus add                                   | re-embedded: the path is part of the embedding input | the new path                                                  |
| Path newly excluded (ignore, protected rename, generated/vendor)    | its chunks dropped                                | its vectors pruned unless another chunk shares them  | none                                                          |
| Chunker version, chunk budget, privacy policy or repository changes | none                                              | none (their keys cover chunker and budget)           | all                                                           |
| Embedding provider, model, version or dimensions change             | all reused                                        | not reused; recomputed for the new identity          | none                                                          |

**Cached indexes and admission.** The scan above is the only source of files for a refresh: the previous index, stat/blob reuse, salvaged schema-1 vectors and the embedding checkpoint can only contribute chunks and vectors that belong to a scanned path or are still wanted by a scanned chunk's input hash. A path that is excluded now (a new ignore rule, a rename whose origin is protected, a vendored directory) is therefore reported as deleted, its chunks are not carried over and its vectors are pruned, and a checkpoint vector for it is ignored and cleared after publication. For that reason `POLICY_VERSION` was not bumped: the reconciliation makes old indexes safe, and bumping it would force every user to rebuild and re-embed. The previous generation stays on disk until the next successful publication (and after a failed one), but it is never returned or retrieved from. Excluded bytes in that not-yet-replaced generation, or in an older checkpoint, remain at rest in the user-owned cache until a refresh completes.

The next index is computed as a value from the previous one, validated, and only then published as a new generation (see above). Reused vectors are copied as rows of packed `Float64Array`s (never through `number[]`); only vectors the provider just returned or a checkpoint supplied are converted, once. Embedding failure, cancellation, request-budget exhaustion, a validation failure or a failed publication leaves the previous complete index canonical. The paid embedding work is not lost: see the embedding checkpoint below. Only missing vectors cost requests, each batch calls `ExternalRequestBudget.reserve` first, batches run sequentially, and without embedding authorization no provider is ever called. The index stage’s event carries counters only (files total, reused, indexed, deleted and read; chunks and vectors reused and created; embedding requests), never paths, source text or vectors. A separate `index_store` stage reports `loaded`, `published`, `cleanup` and `migration_*` events with counts, byte sizes and a generation id only.

**Embedding checkpoint.** `<user-cache>/<repository-namespace>/embedding-checkpoint.json` (`src/retrieval/embedding-checkpoint.ts`) holds completed vectors of a run that did not finish. It is auxiliary: it is never a `RepositoryIndex`, retrieval never reads it, and the canonical index is still built whole, validated and replaced atomically, only after the run succeeds. Entries are the same self-describing `StoredVector` records the index uses (embedding-input hash, provider, model, version, dimensions, chunker version and chunk budget, vector), so it contains no source text and no credentials. A checkpoint vector is reused only when a chunk of the _new_ index hashes to the same input and the same cache key and embedding identity as the entry, exactly as for vectors of the previous index; a changed provider, model, version, dimension setting, chunk budget or chunk content never matches, and a renamed file is re-embedded because the path is part of the embedding input. Reused vectors make no provider call and reserve no request budget. The checkpoint stays JSON on purpose: it only holds the progress of an interrupted run, so it is small next to the canonical index, and its vectors are copied into the packed store once, when the next index is built.

Lifecycle. The file is loaded only when the run is allowed to embed (dry runs and unauthorized runs neither read nor remove it). It is rewritten atomically after every eighth embedding batch, rather than after every vector, and once more when a run fails or is cancelled (provider error, malformed response, exhausted request budget, abort); a failed final index write also checkpoints every vector of the run. A checkpoint write failure is counted and reported but never fails the review, and never masks the error that ended the run. A process killed outright loses at most the batches since the last periodic write. After the canonical index is published the checkpoint is deleted, which also discards entries for chunks that no longer exist or belong to another embedding identity. A corrupt, unreadable or other-version checkpoint is ignored, reported as a value-free diagnostic and overwritten. The index stage event reports `vectorsFromCheckpoint`, `embeddingRequestsAvoided` and `checkpointSaves`; `embedding` stage events (`checkpoint_loaded`, `_hit`, `_miss`, `_saved`, `_save_failed`, `_discarded`, `_cleared`) carry counts only.

**Schema 1 indexes.** Schema 2 added `policyVersion` and the per-file table (content hash, size, blob id). A schema-1 index records neither and neither can be derived from it: the privacy policy its files were admitted under is unknown, and chunk fragments cannot reproduce a whole-file hash. Inventing them would make an old, possibly differently filtered index look validated by the current policy, so a schema-1 index is still never reused as an index. Its _vectors_, however, are self-describing, so `salvageSchemaV1Vectors` (`src/retrieval/index-legacy.ts`) feeds them into the same per-chunk reuse path as a checkpoint: the repository is re-read and re-chunked under the current policy, and a legacy vector is kept only for a current chunk with the identical input hash, cache key and embedding identity. Nothing is re-embedded that did not change; nothing from the old index's structure is trusted. Damaged vector entries are dropped individually.

**Runtime representation and ownership.** A loaded index holds its vectors in a `VectorStore` (`src/retrieval/vector-store.ts`): one segment per embedding space, each a `Float64Array`, plus the cache keys and input hashes as parallel string arrays and the derived squared norms. There is no `number[][]` anywhere in a loaded index: `StoredVector` (a `number[]` per vector) survives only where vectors travel as JSON, namely the embedding checkpoint, schema-1/2 files and what a provider just returned. `test/index-store-structure.test.ts` walks the object graph of a loaded and prepared index and asserts that no number array of vector size is reachable, and that the only large buffer is the one the blob was read into.

Loading is **zero-copy relative to the read buffer**: the loader allocates one buffer of the file’s size, fills it from disk, and every space is a `Float64Array` view of that same memory (the 64-byte header keeps the payload 8-aligned, and the buffer itself starts aligned). The one unavoidable copy is the kernel copying file bytes into that buffer; the numbers are never parsed, converted or re-materialized. If an address were ever misaligned (not the case for this loader), `float64View` copies once into an aligned array instead of reading unsafely, and big-endian hosts swap in place; both are unit-tested. Exact search then scans that same memory: when a space’s rows, in chunk order, are exactly the whole segment in row order, which is what this code writes for the active space, the search index _is_ the segment’s arrays (`packSearchIndex`; asserted by `space.index.vectors === segment.vectors`). Otherwise (vectors no chunk uses, rows out of chunk order, or two chunks sharing one vector) the wanted rows and their norms are gathered into a new array: one copy of the active space, made once per prepared index and not changing any score. The scorer and `retrieveContext` still know nothing about files, JSON or the blob; storage ends where the packed arrays begin, and queries never read from disk.

Steady state is therefore the metadata, one packed vector array per space, one norms array per space, and the key/hash lookup tables, instead of the previous parsed `number[][]` plus the packed array. Temporary duplication exists in two places and ends with them: a **migration** from schema 2 holds the parsed JSON arrays while packing, and they become collectable as soon as the migrated index no longer references them (the parsed document is a local of the loader); and an **incremental refresh that changes vectors** holds the previous store and the next one at once (the next store copies the retained rows with typed-array copies), after which the previous index is unreachable once the refresh returns. When the vector set does not change, the same store object is reused, so there is no second copy at all.

**Norms stay runtime-derived.** Squared norms are not persisted. They are one extra cheap pass over data that must be read anyway, they double as the finiteness check, and persisting them would add a second derived field whose consistency with the vectors would have to be validated (and a stored norm that disagreed with its vector would silently skew scores). The measured cost is small next to reading and checksumming the blob (see the benchmark in `docs/EVALUATION.md`), so there is no case for the extra schema surface.

**Memory mapping.** Node has no built-in memory mapping, and a native addon would be a new dependency and a portability cost. Reading the blob into one buffer already removes the JSON parse, the per-number objects and the second copy, which is where the measured costs were. True mmap (letting the OS page the blob lazily and share it between processes) is a possible later optimization if load time or resident size at 100k+ vectors becomes the limit; nothing here depends on it.

**Migration from schema 2.** Schema 2 (the previous release: one JSON file with every vector as a number array) already contains everything schema 3 needs except the per-chunk input hashes, which are recomputed from the chunk text they describe. `readIndex()` therefore upgrades it in memory (`migrateSchemaV2` in `src/retrieval/index-legacy.ts`): the old file is validated with its old schema, vectors are copied bit-for-bit into packed arrays, vectors made under another chunker or budget (unreachable anyway) are dropped, and the result is reconciled and published as a schema-3 generation by the ordinary refresh, whose manifest replaces the old file last. No provider is called and no embedding budget is used, because no vector is missing; the next run finds a schema-3 index and does not migrate again. Until that final rename the schema-2 file is still the canonical index, so a failed migration (write error, cancellation) leaves it usable and the next run simply retries; a damaged schema-2 file is `corrupt` and an incompatible one (policy, chunker, budget, repository) is `incompatible`, both rebuilt as before. Schema 1 is still not migrated (its vectors are salvaged; see above). The refresh reports `migration_started`, `migration_completed` or `migration_failed` (with the old schema version, vector count, byte size, duration or an error code, never paths, text or values) as `index_store` stage events, not as user-facing output.

**Prepared runtime form.** Retrieval runs on a `PreparedRepositoryIndex`, compiled once per run (`src/retrieval/prepared-index.ts`, `lexical-index.ts`) and shared by every review segment. The inverted `LexicalIndex` maps each term to the ordinals of the chunks containing it, plus lookups from lower-cased symbol name, file path and import needle to their chunks; ordinals ascend in repository order. The score is unchanged: overlap over query-term count, plus import, symbol and same-file boosts, capped at 1. A query now scores only chunks reached through those lists, keeps the best `candidates` by score and then repository order, and appends zero-score chunks in repository order only when positive matches do not fill the limit, which is exactly what the previous full scan’s stable sort produced. Query cost therefore follows posting-list lengths and the number of distinct import needles, not the chunk count; a term present in most chunks still touches most chunks. There is no BM25 or document-length statistic because the scorer uses none. Parity with the reference scan is tested over randomized indexes, and `retrieveContext` still accepts a raw `RepositoryIndex` and prepares it on the fly.

**Exact semantic search.** Semantic retrieval is still exact cosine similarity over every stored vector for the embedding in use; it is not approximate nearest-neighbor search, and its result is bit-identical to the scan it replaced. What changed is the work per query (`src/retrieval/semantic-index.ts`, `semanticSpaceFor` in `prepared-index.ts`):

- **Packing.** The first hybrid query resolves the vectors that `findStoredVector` finds for that embedding identity (provider, model, version, dimensions) in repository order and builds the search space over them: the store’s own row-major `Float64Array` and norms when those rows are the whole segment in order, otherwise a gathered copy (see _Runtime representation_). The space is cached on the `PreparedRepositoryIndex`, so 50 review segments build it once (`prepared.semantic.builds`). It is built lazily, not in `prepareRepositoryIndex`, because an index can hold vectors of several embedding spaces and only the query's adapter says which one to use; lexical-only runs never pay for it. Non-finite values and overflowing norms are rejected when a vector enters a store (a load or a build), inconsistent widths under one embedding identity fail while packing, and a wrong-sized query fails before scoring.
- **Scoring.** The query norm is computed once per query. Each dot product accumulates in dimension order, as before; four rows are scored per pass, each with its own accumulator, so the CPU overlaps four independent additions without reordering any sum. The score is `max(0, dot / sqrt(|q|² |v|²))`, and 0 when either norm is 0.
- **Selection.** A bounded sorted buffer of `candidates` entries replaces allocating a candidate per vector and sorting them all. Rows arrive in ascending ordinal, so a row that only ties the current worst loses and equal scores keep repository order, exactly what the stable sort gave. Candidate objects and `semantic:0.xxx` reasons are created only for the winners.
- **Precision.** Float64 is kept on purpose. Float32 halves memory, but on the project's deterministic test embedder (which produces many exact ties) it changed the top-20 order for 265 of 300 queries and its membership for 52, so it is not exact.
- **Memory.** The loaded index no longer keeps a second, unpacked copy: the vectors exist once, as the packed array the blob was read into, about `vectors × dimensions × 8` bytes plus 8 bytes of norm per vector (12,296 bytes per chunk at 1,536 dimensions, about 293 MiB for 25,000 chunks). Measured figures are in `docs/EVALUATION.md`.
- **Not done.** No ANN structure, quantization, workers or prefilter: semantic-only matches are valid results, so no safe candidate restriction exists. Embedding input hashes are persisted per chunk, so only new chunks are hashed. Query vectors are not cached: every segment query includes its own file name and diff text, so identical queries do not occur within a run.

## Work, request, and time budgets

`maxFiles` and `maxSegmentsPerFile` bound logical review work. `maxRequests` is a separate atomic allowance enforced immediately before every model attempt or embedding call; retries, indexing batches, and query embeddings all consume it. No new provider call starts after cancellation or exhaustion. The total abort signal covers ingestion, Git/GitHub operations, indexing, embeddings, retrieval, retry waits, and model calls. File-diff ingestion is processed in batches of eight and index reads are sequential.

`ExternalRequestBudget` is the one request boundary. Every model attempt (each retry included) and every embedding attempt (each retry included), during indexing or for a query, calls `reserve()` synchronously immediately before the provider is invoked. A reservation either succeeds or throws when the budget is exhausted or the run is aborted. Cache hits never reserve. The budget also keeps the per-kind counts that become `usage.actualRequests` and `usage.embeddingRequests`, so those counters have one source rather than being incremented from concurrent jobs.

## Concurrency, cancellation, and aggregation

Analysis uses a small dependency-free worker pool (`runBounded` in `src/review/pipeline/concurrency.ts`). At most `config.concurrency` files are in flight, and a free worker immediately takes the next file, so one slow request no longer holds back idle workers the way fixed batches did. One file failing never cancels another. Once the total deadline aborts, no further file is started (checked synchronously at start) and in-flight requests are aborted through the shared signal. Each unstarted file is reported as failed and not attempted, with an explicit cancellation error, so an interrupted run is `partial` or `failed` and can never read as complete or clean.

Each file job returns an explicit `FileReviewOutcome` (findings, abstentions, errors, selected context, a `UsageDelta`, completed segment count, failed flag) and writes to no shared state. `aggregateOutcomes()` folds outcomes in eligible-file order regardless of completion order, then deduplicates findings and sorts them by path, first evidence line, and stable ID. Selected context stays in file, then segment, then retrieval-rank order, because rank is meaningful to consumers such as the evaluation harness. Errors and abstentions follow file order.

Usage keeps logical segments, model attempts, embedding calls, all actual external calls, provider-reported current-run tokens, conservative estimates, and cache hits distinct. The prompt budget includes the structured-output schema and message-envelope overhead. The fallback estimator charges one token per UTF-8 byte; it is conservative, not tokenizer-exact.

## Caches and retention

Because request planning changes only which segments exist (never the prompt text or response schema), `PROMPT_VERSION` and the schema version are unchanged: a segment whose text, line map and context are unchanged keeps its key, and a re-segmented request has different assembled messages and therefore a different key. Old entries are simply never hit; nothing is migrated, and every reused entry is still evidence-validated against the segment actually supplied.

Review-result keys cover the exact assembled messages (therefore patch, selected context, bounded PR metadata, and instructions), model name and max output configuration, prompt/schema version, privacy-policy version, and the provider's identity: `ReviewModel.provider` plus an optional non-secret `identity` describing the API contract, such as the endpoint origin and path (`openai-chat-completions/json-schema-v1@…` or `anthropic-messages/json-schema-v1@…`), so `openai:model-x` and `anthropic:model-x` never share an entry. A model name alone is provider-local, so two providers that share a name never share cached answers. Identities never include API keys, URL credentials, query strings, or environment values. Cached objects are schema-validated, and findings are evidence-validated for the current segment before reuse. Provider results are written only after those checks. Cache hits never call the provider and never inflate current-run billed usage. A cache-write failure emits a value-free warning and retains the validated findings and completed coverage. Finding validation preserves the raw count until invalid citations are accounted for; duplicates are deduplicated afterwards. Cache files and the repository index (the manifest, its generation directory and the vector blob, all under the cache directory) remain until explicitly removed (the embedding checkpoint is the exception: it is deleted automatically once the index it fed is published); there is no hidden upload or automatic retention service.

Cache directories are outside the reviewed repository: Windows uses `%USERPROFILE%/AppData/Local/ai-code-reviewer`, macOS uses `~/Library/Caches/ai-code-reviewer`, and Linux uses `~/.cache/ai-code-reviewer`. Each directory name is a SHA-256 namespace derived from the absolute repository path and cache label. Existing repository-local caches are neither read nor automatically migrated: the next run rebuilds them under the trusted user cache. Symlinks and junctions are rejected on cache path components; newly created directories are mode 0700 and files mode 0600 where supported. Existing user-cache directories must belong to the current UID; writes tighten their permissions to owner-only, and reads reject permissive directories. Windows relies on the current user profile's ACLs.

For cleanup, `--local --index --context lexical` reports the exact manifest path. Resolve and inspect its parent directory, then remove only that repository namespace. This discards reproducible review/index artifacts and embedding checkpoints.

## Known limitations

- Secret heuristics are intentionally bounded and can miss novel encodings or produce false positives.
- Compiler parsing retains all source, but symbol metadata is intentionally limited to top-level named declarations; dynamic dependency relationships are not resolved.
- GitHub supplies patches with API size limits; missing patches are skipped and prevent an unjustified clean claim.
- PR retrieval needs a local Git object database containing the head SHA; remote repository trees are not cloned or fetched automatically.
- Token counting uses a conservative byte fallback, not a model-specific tokenizer; provider usage remains authoritative when returned.
- The vector store is a local file set for local/small-to-medium repositories, not a multi-user concurrent service. An index is read whole into memory (about 12 KB per chunk at 1,536 dimensions plus the metadata, roughly 1.2 GiB at 100,000 chunks), and an incremental refresh that changes vectors briefly holds the previous and the next store together. Concurrent index construction remains independent; only filesystem publication and cleanup are serialized.
- Lexical retrieval is posting-list bound: a term that occurs in most chunks (for example `return`) still touches most chunks. Semantic retrieval still compares the query vector with every stored vector.
- The per-file containment check at scan time (one `lstat` and two `realpath` calls) runs on every run, even for unchanged files. Indexes written by schema version 1 are rebuilt from source (their vectors are salvaged, but the index itself is not migrated; see above); schema-2 indexes are migrated in place without re-embedding.
- The vector blob is checksummed in full on every load (about a quarter of the load time at 100,000 vectors) and read into one buffer; loading is not lazy and there is no memory mapping, so the resident size is the whole active index.
- A checkpoint is replaced whole on each write, so a very large unfinished run rewrites a growing file every eight batches; and clearing it after success also drops checkpointed vectors of an embedding identity the successful run did not use.
